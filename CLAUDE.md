## Project Overview

Stacktrace-decoroutinator is a Kotlin library that recovers complete stack traces in exceptions thrown in Kotlin coroutines. It works by intercepting coroutine resumption (`BaseContinuation.resumeWith`) and generating auxiliary "spec methods" at runtime whose names match the coroutine call stack, producing real stack frames when exceptions are thrown.

Targets JVM 1.8+ and Android API 14+ (MethodHandle API requires Android 8+).

## Architecture

### Three installation methods (JVM):
1. **Gradle plugin** (build-time) — transforms bytecode during compilation
2. **Java agent** (runtime) — registers a `ClassFileTransformer` via `java.lang.instrument`
3. **Programmatic API** (runtime) — `DecoroutinatorJvmApi.install()`; uses ByteBuddy to obtain an `Instrumentation` instance, then registers the same transformer as the agent

### Core flow:
```
API Layer → Provider (SPI) → Awakener → SpecMethodBuilder (ASM) → MethodHandle Invoker
```

The awakening mechanism in `common/src/main/kotlin/internal/awakener.kt` captures the coroutine call stack and calls generated spec methods in order, so exception stack traces contain the full coroutine call chain.

### Bytecode processing:
Custom `_plugins/bytecode-processor` Gradle plugin applies compile-time transformations: class renaming, invocation skipping/redirecting, constant loading, static conversion. Processors are configured per-module in individual `build.gradle.kts` files.

### Key conventions:
- Source files are often named by their content (e.g., `api-jvm.kt`, `awakener.kt`, `provider-impl.kt`) rather than by class name
- Version is set once in root `build.gradle.kts` (the `allprojects { version = "..." }` block)
- All published modules use the group `dev.reformator.stacktracedecoroutinator`
- Dependencies are managed via `gradle/libs.versions.toml` version catalog
- Kotlin incremental compilation is disabled (`kotlin.incremental=false` in `gradle.properties`)

### Internal implementation gotchas:

**`$label` high-bit flag**: Kotlin's coroutine state machine sets the high bit (`or Int.MIN_VALUE`) on `$label` when actively executing inside `invokeSuspend` (re-entry guard). Any code using `$label` as an array index must strip the high bit: `label and Int.MAX_VALUE`. The sentinel `NONE_LABEL = Int.MIN_VALUE / 2` means "no debug metadata"; `UNKNOWN_LABEL = NONE_LABEL - 1` means "label field inaccessible". See `tailCallDeoptimize` in `provider-impl.kt` for the canonical guard pattern.

**Raw result values**: The awakener passes raw `Any?` values (not `Result<T>` wrappers) through the coroutine chain. Since `Result<T>` is `@JvmInline`, a `Result.Failure` object IS the raw failure value and `Result.success(x)` at JVM bytecode level is just `x`. Therefore `Result.success(createFailure(e))` correctly delivers a failure to `resumeWith`. The `toResult` extension property is `@SkipInvocations` — a no-op cast at bytecode level.

**`releaseIntercepted()` contract**: Must be called after `invokeSuspend` completes for both success and exception paths, but NOT when it returns `COROUTINE_SUSPENDED`. This mirrors `BaseContinuationImpl.resumeWith` in the standard library.

**Bytecode intrinsics**: `@SkipInvocations` removes the call instruction leaving the receiver on the stack; `@ChangeClassName` renames the class in bytecode; `@ChangeInvocationsOwner` redirects method call owner; `@GetOwnerClass` injects the class literal; `@MethodNameConstant` injects the method name as a string constant.

**`supportsVarHandle` check in `mh-invoker`**: `_supportVarHandle.verifyVarHandle()` in `mh-invoker/src/main/kotlin/internal/mh-invoker.kt` must use `_supportVarHandle::class.java` (not `_support::class.java`) in the `findVarHandle` call. Using the wrong class causes `NoSuchFieldException`, silently disabling VarHandle-based label reads and forcing a slower reflection fallback on every coroutine resume.

**Spec method chain execution order**: Spec methods create a nested real JVM call chain (outermost spec method calls inner, which calls inner, etc.). `DecoroutinatorSpec.$decoroutinator$resumeNext` calls `nextContinuation.callInvokeSuspend` — the `nextContinuation` is always one level *below* the current spec (the spec represents the line number of the frame *above* the continuation it resumes). Execution order: innermost continuation first (via `resumeNext` of the innermost spec), then each outer continuation in turn.

**`DecoroutinatorTransformed`/`DecoroutinatorSpecMethod` split**: `DecoroutinatorTransformed` (class-level) carries `className`/`fileName`/`mode`; per-method data (which methods have an embedded spec method, and what line numbers each handles) lives entirely in a separate `DecoroutinatorSpecMethod` annotation stamped directly on each embedded spec method. `class-transformer/.../class-transformer.kt`'s `generateTransformAnnotation` writes the class-level annotation (called from `transformClassBody` after the separate `generateSpecMethods` call, which stamps the per-method `DecoroutinatorSpecMethod` annotations) — it is deliberately NOT written inside the shared `buildSpecMethodNode` (`spec-method-builder`), because that function is also used by generator-jvm's lazy runtime-generation path (`classLoader-generator.kt`), whose synthetic classes must never carry it (nothing reads it there, and stamping it would be misleading). Only the class-transformer embedded-spec-method path (and its `common/.../transformedClassesRegistry.kt` reader, plus the ASM `AnnotationMetadataResolverImpl` fallback) round-trips this annotation.

**`DecoroutinatorTransformed.className`/`fileName` are written conditionally, not always**: `generateTransformAnnotation`'s `addFileAndClassName` parameter (`transformClassBody` passes `lineNumbersBySpecMethodName.isNotEmpty() && mode.allowSpecMethods`) gates whether the `className`/`fileName`/`fileNamePresent` values get emitted — the exact same condition under which `generateSpecMethods` actually runs and injects the `registerTransformedClass(lookup)` call into the class's `<clinit>`. When that condition is false (either `mode` doesn't allow spec methods, or the class simply has no methods needing an embedded spec method), `registerTransformedClass` is never invoked for that class through this path, so `className`/`fileName` would never be read anyway — omitting them just avoids writing dead annotation data. A reader of `TransformedClassesRegistryImpl.registerTransformedClass` in isolation could be misled into thinking `className` is always the real transformed class name: for a class that *did* get registered (annotation present) but happens to have no `DecoroutinatorSpecMethod`-annotated methods, `className` falls back to the annotation's declared default (`""`), not the real name.

**`name`/`realName` split for obfuscation safety**: `TransformationMetadata.Method` and `TransformedClassesRegistry.TransformedClassSpec.Method` both carry two method-name fields instead of one. `name`/`methodName` is the logical identity baked into the `DecoroutinatorSpecMethod.methodName` *annotation value* at transform time — a string constant that bytecode obfuscation (R8/ProGuard renaming a member) does NOT rewrite — and is what correlates against `StackTraceElement.methodName` for stack-trace matching. `realName`/`realMethodName` is read live via `Method#getName()` (reflective path) or `MethodNode.name` (ASM fallback path) at registration time, and is what must be passed to `MethodHandles.Lookup.findStatic` since it reflects whatever the method is *actually* named right now. This split is why the gradle-plugin's ProGuard rules (`common-gradle-plugin.kt`, `setGeneratingProguardFiles`) can grant `allowobfuscation` to the embedded spec-method members — they can be freely renamed by R8 without breaking lookup or stack-trace correlation. The *class's* own `DecoroutinatorTransformed.className`/`fileName` annotation values are the same kind of logical/non-obfuscated binding key, and — as of the `-keep,allowobfuscation,allowshrinking @DecoroutinatorTransformed class *` rule — the class itself is now also allowed to be renamed by R8; see the "obfuscated and non-obfuscated frames intentionally coexist" entry below for why that's fine.

**Obfuscated and non-obfuscated frames intentionally coexist in the same stack trace — this is a deliberate design, not a bug**: every `StackTraceElement` decoroutinator builds *internally* (`getElementAndSpecMethod` in `awakener.kt`, and anything derived from it) uses the logical/non-obfuscated identity baked into annotations at transform time (`DecoroutinatorTransformed.className`/`fileName`, `DecoroutinatorSpecMethod.methodName`, and — per the entry above — `ManualContinuation`'s cached `SpecCache.element.className`, which is the *same* pattern, not an oversight) rather than whatever R8 actually renamed the real class/method to. It's fine for these non-obfuscated elements to end up directly in the final stack trace, whether via `recoveryExplicitStacktrace`'s explicit patching or via `generator-jvm`'s runtime-generated spec classes (which are defined at runtime via `MethodHandles.Lookup`, so R8 never touches them in the first place — there's nothing *to* obfuscate there). For *embedded* (build-time, not runtime-generated) spec methods specifically, binding a `StackTraceElement` to the right method is done entirely through these same non-obfuscated annotation keys (`TransformedClassesRegistry` lookup by `className`/`fileName`/`methodName`) — both sides of that lookup live in the same non-obfuscated identity space, so it works regardless of what R8 did to the real names. Only *after* the right method is found does its `realName` (see the split above) matter, for the actual `MethodHandles.Lookup.findStatic` call — and that real, obfuscated name is never what appears in a stack trace. Net effect: a single exception's stack trace can freely mix genuinely-obfuscated frames (from ordinary, unmodified execution) with logical/non-obfuscated decoroutinator-fabricated frames, and `tests/.../test-utils.kt`'s `getPossibleUnobfuscatedFrames()` (`sequenceOf(this) + retrace-mapped candidates`) exists specifically to handle both: a genuinely-obfuscated frame gets retrace-mapped back to its original name, while an already-non-obfuscated decoroutinator frame simply has no retrace mapping and passes through as-is via the `sequenceOf(this)` branch. Don't try to make decoroutinator's internal identity strings track R8 renaming — that's not what they're for.

**`SpecCache.specMethod` benign race**: Written without synchronization (two threads may both compute and write the same handle), which is benign since MethodHandle instances are immutable and the computation is pure.

**`ManualContinuation.$decoroutinator$cacheField` can be JVM-null despite its non-null Kotlin type**: The bytecode transformer (`tryAddManualContinuation`) only runs the `PUTSTATIC` for the (`static`) `$decoroutinator$cacheField` in `<clinit>` when `fillUnknownElementsWithClassName` is `true` at class-load time; when false, the raw JVM field stays at its default `null`, even though the interface declares it `val $decoroutinator$cacheField: SpecCache` (non-null). This is only sound because `ManualContinuation.$decoroutinator$cache`'s getter checks `provider.fillUnknownElementsWithClassName` itself and returns `provider.nullElementSpecCache` *before* ever touching `$decoroutinator$cacheField` — since that flag is a process-lifetime-constant `val`, the `<clinit>`-time gate and the getter's runtime gate always agree. Never read `$decoroutinator$cacheField` directly without first replicating that same flag check.

**`ManualContinuation.$decoroutinator$class` is a constant-returning method, not a `<clinit>`-populated field**: unlike `$decoroutinator$cacheField` (a real static field written in `<clinit>`), `$decoroutinator$class`'s synthetic getter (`tryAddManualContinuation` in `class-transformer.kt`) directly embeds `LDC <the class>` + `ARETURN` — no backing field, no `<clinit>` write at all. This used to be a field populated via `PUTSTATIC` at `<clinit>` time (mirroring `$decoroutinator$cacheField`'s pattern), but since the value is always just "this specific transformed class" — a compile-time constant, never actually variable — there's nothing to compute or cache, so the getter can return the class literal directly. This sidesteps the exact class of hazard the entry above documents for `$decoroutinator$cacheField` (JVM-null if queried before `<clinit>` populates it): `$decoroutinator$class` has no initialization-order dependency at all, it's correct from the moment the class is loaded. It's used for a reference-equality check (`javaClass !== \`$decoroutinator$class\`` in `$decoroutinator$cache`'s getter, `provider-api.kt`) to detect when `this` is actually a *subclass* of the whitelisted class rather than the whitelisted class itself — a `LDC <Class>` constant is correctly rewritten by R8 if the class gets renamed (same reasoning as the `name`/`realName` split entry above), so this remains obfuscation-safe without needing a `realName`-style split of its own.

**`LazilyCachedContinuation` vs `ManualContinuation`**: Both bytecode-inject a `ContinuationCached` implementation into external (non-project) classes via `class-transformer/.../class-transformer.kt`, but for different situations. `ManualContinuation` (`tryAddManualContinuation`, whitelist `manualContinuationsInternalClassNames`, e.g. `kotlinx.coroutines.internal.ScopeCoroutine`) is for classes whose real `getStackTraceElement()` is class-wide constant (e.g. always `null`) — it eagerly bakes one synthetic `SpecCache` into a *static* field at `<clinit>`. `LazilyCachedContinuation` (`tryAddLazilyCachedContinuation`, whitelist `lazilyCachedContinuationsInternalClassNames`, e.g. `kotlinx.coroutines.debug.internal.DebugProbesImpl$CoroutineOwner`) is for classes whose real `getStackTraceElement()` carries genuine, varying per-*instance* data — it lazily computes and caches a `SpecCache` into an *instance* field the first time `$decoroutinator$cache` is read, which is always correct because a real per-instance value never changes after construction. Both mechanisms also patch the class's own `getStackTraceElement()` (via the shared `updateGetStackTraceElementMethod`) to serve the cache once populated, so external callers of that method benefit too — but the two patches call *different* things to fetch the cache, and this difference is load-bearing: `ManualContinuation`'s patch calls the smart `$decoroutinator$cache` getter (safe — its computation never calls back into `getStackTraceElement()`), while `LazilyCachedContinuation`'s patch calls the *raw* `$decoroutinator$cacheField` getter, not the smart `$decoroutinator$cache` getter. Calling the smart getter there would recurse infinitely: `$decoroutinator$cache`'s own computation calls `getStackTraceElement()` to get the real value, which — if patched to call the smart getter — would re-enter `$decoroutinator$cache` before the field is ever populated.

**`SpecCache.element` is nullable; `provider.nullElementSpecCache`** is the shared singleton (`element = null`, `specMethod` pre-set to `methodHandleInvoker.unknownSpecMethodHandle`) used whenever a `ManualContinuation`/`LazilyCachedContinuation` frame has no usable element and `fillUnknownElementsWithClassName` is off. Reusing one singleton (rather than returning plain `null`) means the caller — the injected `$decoroutinator$cache` field-based caching — never has to distinguish "not yet computed" from "computed, nothing useful," so it never recomputes.

**`Method.invoke` wraps checked exceptions in `InvocationTargetException`**: When calling a protected/private method via reflection (e.g., `ClassLoader.findClass`), any checked exception thrown by the method is wrapped in `InvocationTargetException`. Direct `catch (e: ClassNotFoundException)` at the call site of `Method.invoke(...)` will NOT catch it — you must catch `InvocationTargetException` and rethrow `e.cause`. See `generator-android/spec-methods-factory-generator-android.kt`'s `ClassLoader.findClass` extension for the canonical pattern.

**`ArtifactWalker.onFile` stream ownership**: The `reader: () -> InputStream` lambda creates a new stream per call. **The caller owns the stream and must close it** — neither `ZipArtifactBuilder.addFile` nor `DirectoryArtifact.addFile` closes the `body` parameter. Always wrap in `reader().use { ... }` or `(expr).use { ... }`.

**`classBodyResolver` must not trigger class loading**: `transformClassBody`'s `classBodyResolver: (className: String) -> InputStream?` parameter is called during class transformation (inside a `ClassFileTransformer` callback). Implementations must use `ClassLoader.getResourceAsStream` (reads raw bytes) rather than `Class.forName`/`ClassLoader.loadClass`, because class loading from within a class-loading callback causes recursive loading and `ClassCircularityError`. The `className` argument is a dotted binary name (e.g., `com.example.Foo$Bar`); in the agent path, convert to a path with `className.internalName + ".class"`. This is why the enum `DecoroutinatorMetadataInfoResolveStrategy` (and its `CLASS`/`SYSTEM_RESOURCE_AND_CLASS` strategies) was removed in #81.

**`tailCallDeoptimize` NONE_LABEL vs UNKNOWN_LABEL distinction**: Both sentinels have bit 31 set, but `tailCallDeoptimize` in `provider-impl.kt` treats them differently. The guard `label != NONE_LABEL && label and Int.MIN_VALUE != 0` means: NONE_LABEL (class has no metadata, `_elementsByLabel == null`) → condition is false → wrap the completion anyway (safe, since no re-entry risk). UNKNOWN_LABEL (field inaccessible) → condition is true → skip wrapping, treating it as "possibly executing" (conservative, avoids wrapping a running coroutine). This asymmetry is intentional: unknown metadata is conservative in the "wrap" direction; inaccessible field is conservative in the "don't wrap" direction.

**`SpecMethodsFactoryImpl.init` listener-then-snapshot**: The `init` block adds the listener first, then iterates `transformedClasses` under `classSpecsByNameUpdateLock`. This ensures no class is missed: any class registered before the listener was added is caught by the snapshot iteration, and the listener callback itself acquires the same lock so it cannot race with the snapshot. A class registered concurrently may be processed twice (listener call + snapshot entry), but `register` is idempotent (harmless overwrite).

**`Artifact.transform` two-pass walk in `gradle-class-transformer.kt`**: First pass processes all non-module-info files (transforms class bytecode, accumulates `readProviderModule`/`containsBaseContinuation` flags). Second pass processes only module-info files (patches `requires`/`provides` based on first-pass results). `doesNeedTransformation` may stop the first pass early via `onFile` returning `false`, which also skips the second pass — but this is correct because `doesNeedTransformation` only needs a boolean. `transformTo`'s `onFile` always returns `true`, so both passes always complete when doing actual transformation.

**Groovy DSL initialization via `@file:ChangeClassName`**: `gradle-plugin/src/main/kotlin/groovy-dsl-initializer.kt` is an intrinsic placeholder with `@file:ChangeClassName(toName = "...GroovyDslInitializer", deleteAfterChanging = true)` that defines `fun initGroovyDsl(target: Project): Unit = fail()`. At Kotlin compile time, the call `initGroovyDsl(target)` in `common-gradle-plugin.kt` resolves to this Kotlin function. After bytecode processing, all references to the Kotlin file class are replaced with `GroovyDslInitializer` (the Groovy class in `src/main/groovy/GroovyDslInitializer.groovy`), and the Kotlin placeholder class file is deleted. The Groovy class has the real `static void initGroovyDsl(Project)` that registers Groovy DSL extension methods. This avoids `ServiceLoader.load(...)` which uses the thread's context classloader — on Gradle 9 build-operations worker threads, the context classloader doesn't include the plugin JAR, causing `NoSuchElementException`.

**`BytecodeProcessorContext.Key<T>.isEmpty` must be defined per key**: Every `Key<T>` (`asm-plugin-api.kt`) must implement `isEmpty(value: T): Boolean` alongside `default`/`merge`, so `BytecodeProcessorContextImpl.merge` (in-memory) and `MapperBytecodeProcessorContext.merge`/`get` (the Jackson-JSON-persisted context in `gradle-plugin/bytecode-processor-gradle-plugin.kt`, backing `compileContext_<task>.json`/`mergedContext.json`/`initialContext.json`) can drop an entry instead of persisting an empty `Map`/`Set`. Deliberately not inferred via a generic `is Map<*,*>`/`is Collection<*>` runtime check — each `Key` declares emptiness explicitly so a future non-collection-typed key can't be silently misclassified as "never empty". Dropping the entry is safe only because `key.default` is the identity element for `key.merge` on every current key (`value1 + value2` union with an empty default), so an absent entry and a present-but-empty one read back identically via `get`.

**`DecoroutinatorTransformed.Mode` gates every class-layout-changing step, including reparenting onto `DecoroutinatorSpecImpl`**: `transformClassBody` (`class-transformer/.../class-transformer.kt`) takes a `mode: DecoroutinatorTransformed.Mode` (`FULL`/`SKIP_SPEC_METHODS`/`PRESERVE_CLASS_LAYOUT`, ordinal order = strongest to weakest) instead of the old standalone `canChangeBaseContinuationHierarchy`/`skipSpecMethods` booleans. `mode.allowChangingClassLayout` (`!= PRESERVE_CLASS_LAYOUT`) gates: reparenting a class onto `DecoroutinatorSpecImpl` (`trySetSpecImplAsBaseClass`, superName + `<init>`'s `INVOKESPECIAL` retarget, mirroring the old `BaseContinuationImpl`-only logic but now also attempted for any class that gets a `BaseContinuationExtractor`/`ManualContinuation`/`LazilyCachedContinuation` interface added), saving tail-call caches, and adding those marker interfaces at all. `PRESERVE_CLASS_LAYOUT` exists because `Instrumentation.redefineClasses`/`retransformClasses` forbid hierarchy/structural changes on an already-loaded class: `jvm-agent-common/.../class-transformer-jvm-agent-common.kt` passes `PRESERVE_CLASS_LAYOUT` whenever `classBeingRedefined != null` (unless `isRedefinitionChangingClassLayoutAllowed`, which **defaults to `false`**), `FULL` on a genuine first load; the Gradle-plugin build-time path (`gradle-class-transformer.kt`, patches the stdlib jar bytes before anything loads them) always passes `FULL`/`SKIP_SPEC_METHODS`, never `PRESERVE_CLASS_LAYOUT`. A class that already carries a `DecoroutinatorTransformed` annotation is never re-transformed except to `error()` if the newly-requested `mode` is *stronger* (lower ordinal) than the one recorded — so that annotation's `mode` field is now load-bearing, not just descriptive.

**`mode` records what was *permitted*, not which specific sub-operation succeeded**: all three downgrade sites in `transformClassBody` (`class-transformer.kt`) — tail-call caches, spec methods, and `trySetSpecImplAsBaseClass(apply)`'s reparenting — only set `preserveClassLayout`/`skipSpecMethods` when there was something applicable to do *and* the incoming `mode` blocked it (mirrors `if (tailCallCaches.isNotEmpty()) { if (mode.allowChangingClassLayout) ... else preserveClassLayout = true }`). `trySetSpecImplAsBaseClass()` returning `false` because a class's `superName` isn't `java.lang.Object` (true for essentially every class except `BaseContinuationImpl` itself — user continuation classes extend `SuspendLambda`/`ContinuationImpl`, `ManualContinuation`/`LazilyCachedContinuation`-whitelisted kotlinx.coroutines classes extend their own library base classes) is "not applicable here," not "blocked by `mode`" — same category as zero tail-call caches — so it correctly does *not* downgrade `mode`. The class still gets whatever else `FULL` permission covers (e.g. the `ManualContinuation`/`BaseContinuationExtractor`/`LazilyCachedContinuation` interface, which *is* a real, successful layout change). Nothing in the codebase infers "hierarchy was definitely changed to `DecoroutinatorSpecImpl`" from `mode == FULL` — `buildSpecInfo`'s `specHolder` reuse (`common/.../awakener.kt`) always does `as? DecoroutinatorSpecImpl` defensively regardless.

**`buildSpecInfo`'s `specHolder` reuse never double-uses an object, even though it looks branch-inconsistent**: Each loop iteration in `common/.../awakener.kt`'s `buildSpecInfo` calls `getElementAndSpecMethod` on a different object than every other iteration — the traversal (`.completion`/`.callerFrame`) only ever moves forward and never revisits a node. `currentSpecHolder` is always set to *that same object* (`completionCopy`/`frameCopy`) regardless of which of the three branches ran. It's consumed as a spec's backing store either immediately in the same iteration (if `specHolder` was `null` coming in) or with a one-iteration delay (if not — see the `specHolder.let { ... }` dispatch in the tail); either way, a given object backs at most one `DecoroutinatorSpec`, so there is no aliasing between two spec nodes. Critically, `currentSpecHolder` does *not* need to equal `currentBaseContinuation`/`currentFrame` (the cursor the *next* iteration will process) for this to be safe — that equality only happens to hold in the steady-state `BaseContinuation` branch, where `completionCopy` (fetched from `baseContinuationCopy.completion`) already *is* the next cursor. In the foreign-`CoroutineStackFrame` branches there's an extra explicit `.callerFrame` hop *after* the fetch, so the object being reused and the next cursor are different objects — this is not a bug: the reused object's `nextContinuation` is `null` in those specs anyway (there's nothing of ours to resume once we've left the `BaseContinuation` chain), so it's purely borrowed scratch memory, never referenced again. In the steady-state branch, the reused object also happens to be that same spec's own `nextContinuation` — a harmless self-reference where one JVM object simultaneously wears the `DecoroutinatorSpecImpl` hat and the `BaseContinuation` hat it will later be resumed through via `resumeNext`. Don't "fix" the transition/frame-walk branches to source `currentSpecHolder` from `currentFrame` instead of `completionCopy`/`frameCopy` — that was tried and reverted; it changes nothing about correctness and only obscures that the reused object and the next cursor are allowed to differ.

**`specHoldersInternalClassNames` reparents classes purely for `specHolder` reuse, no marker interface needed**: `class-transformer.kt`'s third reparenting block (after `BaseContinuationImpl` and the `BaseContinuationExtractor`/`ManualContinuation`/`LazilyCachedContinuation` one) targets classes like `kotlinx.coroutines.JobSupport` — implements only interfaces, so its real `superName` is `java.lang.Object`, satisfying `trySetSpecImplAsBaseClass`'s precondition — but has no per-instance `getStackTraceElement()` state worth caching and isn't itself a per-suspend-function continuation. Unlike the other whitelists, this one adds *no* marker interface or field; it purely reparents the class so instances can serve as a `buildSpecInfo` `specHolder` reuse candidate if they ever show up as a completion/frame object (kotlinx.coroutines `Job`/`Deferred` implementations are often also `Continuation`s). `trySetSpecImplAsBaseClass(apply: Boolean)` follows the same check-only-vs-mutate shape as `tryAddManualContinuation`/etc.: `apply = false` only tests eligibility (`!isInterface && superName == Object`) without mutating — which is exactly what lets the `PRESERVE_CLASS_LAYOUT` branch correctly set `preserveClassLayout = true` only when there was a genuine blocked opportunity, per the "`mode` records what was permitted" entry above. Calling `trySetSpecImplAsBaseClass(true)` twice on the same already-reparented node is harmless (the second call sees `superName != Object` and returns `false`), so there's no risk even if a class were ever added to more than one of these whitelists.

**ASM `FrameNode` local/stack arrays need `arrayOf<Any>(...)`, not `arrayOf(...)`, whenever the array mixes element types**: `spec-method-builder/.../spec-method-builder.kt` builds `FrameNode(type, nLocal, local, nStack, stack)` calls where `local`/`stack` mix `String` (`Type.internalName`) and `Int` (`Opcodes.INTEGER`/`TOP`/etc. sentinel constants) elements, per ASM's `Object[]`-typed API. Kotlin's `arrayOf(...)` infers its element type from the arguments given: for a uniform-type array (the `stack` arrays here, all `String`) that lands on `Array<String>`, which Kotlin happily passes where `Object[]` is expected. For a genuinely mixed-type array (the `local` arrays, `String` + `Int`) the inferred type is *not* `Any`, and the result no longer type-checks as the `Object[]` parameter — an explicit `arrayOf<Any>(...)` is required. Easy to reintroduce by "simplifying" a `FrameNode` call back to bare `arrayOf(...)`.

**`_plugins/delete-signature-checksums` shrinks the Maven Central Portal file count by deleting checksums *of* GPG signatures**: Publishing goes through the `com.gradleup.nmcp` plugin, which registers a real local `maven-publish` repository named `"nmcp"` (`build/nmcp/m2` per module) and stages every publication there before a separate aggregation step zips and uploads that directory to Central Portal. Gradle's own `maven-publish` machinery auto-generates `.md5`/`.sha1` checksum sidecars for *every* file written to a Maven-format repo — including the `.asc` GPG signature files the `signing` plugin attaches as extra publication artifacts — which is pure file-count bloat: a `.asc` file is already a cryptographic signature, so a checksum of it (`.asc.md5`/`.asc.sha1`) adds nothing Central actually needs to verify. `DeleteSignatureChecksumsPlugin` (`_plugins/delete-signature-checksums/src/main/kotlin/delete-signature-checksums.kt`) hooks `doLast` on every `PublishToMavenRepository` task and deletes any `*.asc.{md5,sha1,sha256,sha512}` file from that task's repository directory (skipped entirely for non-`file://` repos, so it's a no-op against remote/HTTP targets). Running in `doLast` on the *same* task that wrote the files — rather than a separate task wired in with `mustRunAfter`/`finalizedBy` — is what makes the ordering safe: Gradle only starts nmcp's downstream zip/aggregation task (which lazily walks that same directory) after this task's entire action list, cleanup included, has finished. Applied per-module (via `alias(libs.plugins.delete.signature.checksums)`, right after `signing` in each `plugins {}` block) rather than once at the root, matching how `dokka`/`maven-publish`/`signing`/`force-variant-java-version` are already applied individually per publishing module in this codebase. Verify the effect with `./gradlew nmcpZipAggregation` and inspect the resulting zip.

**`DispatchingProvider` (`jvm-agent/src/main/kotlin/internal/dispatching-provider.kt`) routes every `DecoroutinatorProvider` call by the classloader that actually *defines* kotlin-stdlib for the target object, not the target object's own classloader**: jvm-agent's single `ClassFileTransformer` can be asked to transform a class loaded by *any* classloader in the JVM, but `common`'s `Provider` has real, load-bearing references to `kotlin.coroutines.jvm.internal.*` — whichever classloader *defines* `common`'s `Provider` class must itself resolve that same kotlin-stdlib copy. `entryFor(loader)` resolves the *real* key by loading `kotlin.coroutines.Continuation` (`CONTINUATION_INTERFACE_NAME`) through the target's own loader and taking *its* defining classloader — not `loader` itself — because an application classloader very often doesn't define kotlin-stdlib classes itself, only delegates to a parent that does; keying on the delegate-resolved loader means two different target classloaders that both delegate to the *same* real kotlin-stdlib source correctly share one embedded `common` copy instead of building a redundant duplicate (the `entriesByLoader[kotlinStdlibLoader] = result` line inside the `optimisticLockGetOrPut` generator, on top of the outer `this[key] = ...`, is what makes that second, coarser lookup available to future callers keyed by a *different* `loader` that resolves to the same `kotlinStdlibLoader`). `DispatchingProvider` embeds `common`'s compiled jar as a base64 string constant (chunked across `commonResidualJarBase64Chunk0..7` — a single `CONSTANT_Utf8_info` is capped at 65535 bytes) and, per resolved kotlin-stdlib-defining classloader, decodes a fresh `DecoroutinatorCommonClassLoader(commonResidualClasses, targetLoader)` parented directly on it. The common (single-classloader) case — where the agent's own loader already resolves a real kotlin-stdlib, e.g. the host app's — skips all of this: `defaultEntry` is built *eagerly* at construction (never `by lazy`, to avoid a volatile read on every hot-path `entryFor` call — cheap on x86, not free on ARM), and the `WeakHashMap`-backed per-classloader map is only ever allocated when dispatching is genuinely needed (`forceAgentClassLoaderDispatchingProvider` runtime setting, or `hasKotlinStdlibVisible(defaultLoader)` actually returns false). That map is deliberately *not* wrapped in `Collections.synchronizedMap` — `entryFor` reads/writes it only through `optimisticLockGetOrPut` (`provider/.../utils-provider.kt`: an unsynchronized optimistic read, falling back to a `ReentrantLock` only on a miss or a raced `ConcurrentModificationException` — the same pattern `spec-methods-factory-provider.kt`/`stacktraceElementsFactory.kt` already use), so an extra synchronized wrapper would just be redundant locking on top of that; the nested reads/writes inside the generator lambda are safe because they run while `entriesByLoaderLock` is already held by the outer `optimisticLockGetOrPut`.

**`DecoroutinatorProvider.callInvokeSuspendIfResultIsNotCoroutineSuspended` replaces three separate members (`getCoroutineSuspendedMarker`, `probeCoroutineResumed`, `createFailure`)**: the old shape required the caller (`DecoroutinatorSpecImpl.$decoroutinator$resumeNext` in `provider-api.kt`) to fetch the `COROUTINE_SUSPENDED` marker across the provider boundary just to compare `result !== marker`, then separately invoke `probeCoroutineResumed`/`createFailure` through their own method references — each of those is a `DispatchingProvider`-routed call in jvm-agent (its own `entryFor` classloader lookup), so a single resume could pay for that lookup three—four times over. Now the entire "is this actually a resume, and if so run `invokeSuspend`/`probeCoroutineResumed`/`createFailure`/`releaseIntercepted`" sequence is one `DecoroutinatorProvider` method, so it costs exactly one `entryFor` lookup, and the raw `COROUTINE_SUSPENDED` singleton (whose identity is itself classloader-specific — see the entry above) never has to cross the provider API boundary at all: `common`'s `Provider.callInvokeSuspendIfResultIsNotCoroutineSuspended` compares against its own in-classloader `COROUTINE_SUSPENDED` directly (`common/.../utils-common.kt`'s inline `BaseContinuation.callInvokeSuspend` extension does the actual work).

**`BaseContinuationAccessor` caching must be scoped per target classloader, not process-wide**: `DecoroutinatorProvider.getBaseContinuationAccessor`/`prepareBaseContinuationAccessor` build a `BaseContinuationAccessor` — a set of `MethodHandle`s bound via `MethodHandles.Lookup` to one specific `BaseContinuationImpl` `Class` object — and used to cache it in a single process-wide `var` in `provider-api-internal.kt`. That's wrong whenever more than one classloader defines a class named `BaseContinuationImpl` in the same process (jvm-agent's per-target dispatching; also any plugin/module-reload scenario in general): JVM class identity is `(defining classloader, name)`, not bytecode content, so two independently-loaded `BaseContinuationImpl` classes — even from byte-identical kotlin-stdlib jars — are genuinely distinct `Class` objects, and invoking the first one's cached handles against an instance of the second throws `ClassCastException`. kotlinx.coroutines' `runBlocking` treats that as a *fatal internal error* rather than propagating it, so it surfaces as a silent hang, not a clean failure. The cache now lives as instance state on `common`'s `Provider` (one instance per target classloader, courtesy of `DispatchingProvider`), and both members are `DecoroutinatorProvider` interface methods, routed by `DispatchingProvider` like everything else. `getBaseContinuationAccessor` takes a `baseContinuation: Any` parameter — needed because the bytecode `class-transformer.kt` injects into `BaseContinuationImpl.resumeWith` calls it *before* `MethodHandles.lookup()` even runs, to keep the cached fast path cheap (`ALOAD 0` vs. a real `MethodHandles.lookup()` call). `prepareBaseContinuationAccessor` doesn't need that parameter: `lookup.lookupClass()` is *always* that same `BaseContinuationImpl` (`transformBaseContinuation()` only ever injects `MethodHandles.lookup()` into `BaseContinuationImpl`'s own `resumeWith`), so `lookup` alone already carries the same routing identity.

**Building a module usable when kotlin-stdlib is genuinely absent from the process's system classpath**: `tests/no-kotlin-stdlib` (used by `jvm-agent:tests-no-kotlin-stdlib`/`jvm-agent:jdk8-tests-no-kotlin-stdlib` — see Test modules above) follows the same recipe `provider`/`runtime-settings` already use to stay free of real kotlin-stdlib runtime calls: apply `RemoveKotlinStdlibProcessor` (strips the compiler-generated `Intrinsics.checkNotNull*`/`throwIllegalArgument`-etc./`emptyMap`/`emptyList`/`emptySet`/`collectionSizeOrDefault`/`closeFinally`/`kotlin._Assertions.ENABLED`/`Unit.INSTANCE` calls ordinary Kotlin code compiles to — see `_plugins/bytecode-processor/plugins/src/main/kotlin/removeKotlinStdlib.kt` for the exact allowlist), and give the module a real `module-info.java` with `requires kotlin.stdlib;` — needed only so `kotlinc` can compile at all (every Kotlin class carries a structural `@kotlin.Metadata` annotation reference); the processor strips this same `requires` clause from the compiled `module-info.class` afterward, same as `provider`/`runtime-settings`. Two things beyond that existing recipe were needed here specifically: (1) the Kotlin Gradle plugin adds `kotlin-stdlib` as an *implicit* dependency by default, and nothing overrides that at the root `gradle.properties` (`provider`/`runtime-settings` are fine keeping it — they're published artifacts consumed by apps that already have kotlin-stdlib) — a module that must have *no* real kotlin-stdlib dependency edge needs its own `gradle.properties` with `kotlin.stdlib.default.dependency=false`, plus an explicit `compileOnly(dependencies.kotlin("stdlib", <version>))` so `kotlinc` still sees it at compile time; (2) `alias(libs.plugins.force.variant.java.version)` is required too, or Gradle's dependency resolution reports the module's `TargetJvmVersion` as 9 (from `java.sourceCompatibility`, needed only for `module-info.java`) even though the actual Kotlin bytecode targets 8 (`kotlin.compilerOptions.jvmTarget`), which silently blocks any JDK-8-toolchain consumer (`jvm-agent:jdk8-tests-no-kotlin-stdlib`) from depending on it at all. Source in such a module must also avoid any real (non-inline) kotlin-stdlib call the processor's allowlist doesn't cover — no lambdas/higher-order functions, no `by lazy`, no kotlin collection-literal functions; `provider/src/main/kotlin/internal/di-provider.kt` is the reference style already working under this constraint.

**Test code uses `runBlockingWithTimeout`, not raw `kotlinx.coroutines.runBlocking`**: `tests/src/main/kotlin/test-utils.kt` defines `runBlockingWithTimeout(timeout = 3.seconds, context = EmptyCoroutineContext, block)` — it runs `block` via ordinary `runBlocking` on a background `Thread`, `join(timeout)`s it, and `fail()`s with a clear message if it didn't finish in time, rather than hanging forever. This exists because a real bug once did exactly that: the process-wide `BaseContinuationAccessor` cache (see the entry above) surfaced as kotlinx.coroutines silently deadlocking a `runBlocking` call under `CoroutinesInternalError`, not as a clean exception — a plain `runBlocking` gave no signal something was wrong beyond the test hanging, and it took a `jstack` dump to diagnose. Every test in `tests/src/main/kotlin/{runtime-test.kt,performance-test.kt}`, `tests/methods-with-spaces-tests`, `jvm/jdk8-tests/example.kt`, and the `_tests/{jdk8,jvm,android,android-legacy}/gradle-plugin-tests` compatibility suites now calls `runBlockingWithTimeout` instead — same call-site shape as `runBlocking { ... }`, since it's a plain top-level function in the same `dev.reformator.stacktracedecoroutinator.tests` package as `checkStacktrace` (no import needed within `tests` itself; an explicit `import dev.reformator.stacktracedecoroutinator.tests.runBlockingWithTimeout` elsewhere). `performance-test.kt`'s `resumeWithDepth` passes an explicit `timeout = 30.seconds` — its 100-iteration loop (each iteration `Thread.sleep`s at least 10ms) can exceed the 3-second default on a loaded machine, and the point there is a hang safety-net, not a tight bound. Three modules deliberately keep raw `runBlocking` instead: `_tests/{jdk8,android}/wrong-generator-tests` and `tests/custom-loader`'s `ClassWithSuspendFunctionsStub` are all intentionally isolated from the `tests` module/artifact (minimal, deliberately narrow dependency sets — `tests:custom-loader`'s stub in particular is driven through an isolated classloader by `NoKotlinStdlibTest`, see `DispatchingProvider` above), so adding `runBlockingWithTimeout` there would mean adding a new dependency edge, not just renaming a call.
